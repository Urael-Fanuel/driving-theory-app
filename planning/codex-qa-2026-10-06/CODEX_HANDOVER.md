## 2. What changed and why (with the risk to look for)

### A. Platform upgrade 54 -> 57
`package.json`, `package-lock.json`, `app.json`, `tsconfig.json`. expo-av was removed; audio is now
`expo-audio`, video is `expo-video`. `app.json` has a top-level key `"react-native-google-mobile-ads":
{"android_sdk":"classic"}` that works around a Gradle bug in ads library 17.2.0 on Expo (it makes
`expo start` print "Root-level expo object ... ignoring extra key"; intentional).
Look for: leftover expo-av imports, plugin config mistakes, manifest permissions beyond
RECORD_AUDIO / INTERNET / ACCESS_NETWORK_STATE / MODIFY_AUDIO_SETTINGS plus what the location and ads
plugins add (check the **merged** manifest of the built APK), background audio must be off.

### B. Audio playback (highest risk area)
- `services/sound.ts` (new, 336 lines): a wrapper that imitates the old expo-av `Sound` API on top of
  expo-audio. Adds an "interrupted" state: when Android takes audio focus (call, YouTube) expo-audio pauses
  natively and the app used to show a false "playing" state (silent ⏸). Now detected and exposed through
  `hooks/useAudioInterrupted.ts`.
- `hooks/useAudio.ts` (447 lines changed): every playback request takes a ticket (`_claim()`) **before any
  await**, so a later request cancels earlier ones and two voices can never overlap. Safety clock
  `CLIP_SAFETY_MS = 150000` is held while paused/interrupted. `playAndAwaitAudio`, `playAudio`,
  `playPreloadedAudio`, `stopAudio`.
- `utils/googleTTS.ts`: same interruption handling for the TTS path.
- Screens wired to the interruption signal in both engines: behavioral-subtopic, topic-quiz,
  exam/practice, `AudioFeedback`, `TextFeedback`, `LocationPermissionModal`, `SponsorAdBanner`.
- `components/shared/VideoModal.tsx`: `audioMixingMode='mixWithOthers'` so the sign-302 video does not take
  exclusive audio focus and stop the explanation. 302 is the only sign with a video, on purpose.
- `services/audioCache.ts`: downloads are atomic (`downloadAtomic`: temp name, size/HTTP checks, rename),
  `hasUsableCopy` (>= 1 KB), `discardCachedCopy` self-heal (bad saved copy is removed and the original URL
  is played once).
Look for: races between ticket release and status callbacks, an interruption that never clears,
a clip that never finishes (safety clock), listeners not removed, unload while playing, behavior differences
between expo-av and expo-audio (position/duration/didJustFinish semantics).

### C. Diagnostics
`services/errorReporter.ts` (new, 710 lines) and migration
`supabase/migrations/20261001000000_client_errors_diagnostics.sql` (already applied live: the table
`client_errors` has `category, details, app_version, platform, device`; 54 rows, see section 3b).
One file per pending report in `diagnostics/`, `diag_fatal.json` for crashes, byte budgets measured as UTF-8
plus jsonb spacing against the table check `octet_length(details::text) <= 8000`, RLS policy
`user_id IS NULL OR auth.uid() = user_id`, throttle per session, `sanitizeText` redacts URLs/tokens/JWTs/keys/
emails. Look for: infinite retry of a rejected row, queue growth on a full disk, anything personal leaking,
reports lost when offline, startup cost.

### D. Loading speed and robustness
`backend/supabaseClient.ts` (`fetchWithDeadline` + breaker), `backend/topicsLoader.ts` (stale-while-revalidate,
AsyncStorage key `topics_cache_v1:<build>`), `backend/fallbackTopics.json`, `backend/api.ts`,
`services/identity.ts` (`resolveUserId`: waits 5 s for session / 15 s for sign-in and **never mints a new
anonymous user because of slowness**), `contexts/EngineContext.tsx` (a returning user is unblocked
immediately from saved prefs). Look for: a path that creates a second anonymous user (progress loss),
a stuck loading screen, cache never refreshed, a deadline that cancels a legitimate long request
(audio/image downloads must not be cut by it).

### E. Bundled system audio
`services/bundledAudio.ts` + `assets/system-audio/*.mp3` (16 files, ~600 KB: welcome, mode explanations,
exam pass/fail, TTS error clips, offline notice, number_1..4, try_again). `services/sound.ts` prefers the
bundled copy; `audioCache.ts` skips bundled names and deletes old downloaded copies at startup.
Look for: a filename in the code that is not in the map (falls back to network on a first offline launch),
APK size, duplicate storage.

### F. Interface text
`constants/strings.ts` `UiStrings` (12 strings, authored by Gemini, approved by the owner) used in:
engineA home, engineA behavioral, engineA behavioral-subtopic, engineB home, engineB progress,

underDevTitle, underDevBody, backToList, topicLabel, shareApp, shareSuccess, a11yBack, a11yShare, a11yLevel(n),

### 3b. What the live `client_errors` table and an audio audit show (read-only, 2026-10-06)

54 rows. 21 are old-style (before the new reporter: failed API calls only, message lost as
"[object Object]", no user id, 09-22 to 10-01). 33 are new-style, **all from one Samsung SM-S931B (the owner's
test phone)** running test builds `1.0.0 (9)` on 10-05/10-06 and Expo Go today. Production v8 has no new
reporter, so there is **no field data from real users yet**. Findings:

1. **HTTP 429 (25 rows, `preCacheAudioBatch` / `downloadInBackground`):** storage answers "too many requests"
   when the app pre-downloads question audio in batches of 5 (`services/audioCache.ts` `BATCH_SIZE = 5`).
   A burst of ~60 HEAD requests from the implementer's PC was also answered 429, so the threshold is low.
   Hypothesis, not proven: this may be part of the "audio goes silent after the first session on some
   phones" complaint. Please assess pacing / retry-with-delay and what the player does after a 429.
2. **HTTP 400 (13 distinct files):** names like `beh_mind_safety_0_0_0.mp3` and
   `answer_beh_mind_safety_0_0_0_B.mp3` exist neither in storage nor in the database. They are built by a
   fallback in engine A (`app/(engineA)/(tabs)/exam.tsx` lines ~355 and ~428:
   `${_AUDIO_BASE}/${qId.toLowerCase()}.mp3` and `answer_${qId}_${answer?.id}.mp3`) for behavioral questions,
   whose real audio is read by TTS (`backend/api.ts` builds ids `beh_<topic>_<l>_<s>_<q>` with
   `question_audio_url: undefined`). Pure waste plus false error reports plus extra pressure on the rate limit.
   Please check engine B and the prefetch lists for the same fallback.
3. **Two real missing files in production, FIXED 2026-10-06:** the database referenced
   `answer_716_q3_A.mp3` and `answer_724_q3_C.mp3` (topic `traffic_lights`) but the files were not in the bucket
   (the sibling answers exist; the original upload had silently failed in March). The implementer regenerated
   exactly these two with the project's own TTS pipeline from the unchanged live text (isolated working folder,
   no other file generated) and uploaded exactly these two, no database change. Verified from outside through
   the exact database URL: HTTP 200, audio/mpeg, byte-identical. Re-audit: 8148 files in the bucket, 6051 distinct
   files referenced, **3 dangling references left**: the intro clips `topic_warning_intro.mp3`,
   `topic_regulatory_intro.mp3`, `topic_right_of_way_intro.mp3` (frozen topics; do not touch; please check
   whether the app ever plays them).
5. **A single failed clip silences the rest of the answers (by design, but costly):** in engine A
   (`app/(engineA)/question/[id].tsx` ~line 217, same pattern in the other engine-A screens)
   `if (!await playAndAwaitAudio(answerUrl, isCancelled)) { ...; return; }` aborts the whole read-aloud sequence
   when one clip fails (documented in `hooks/useAudio.ts`: `false` = the user heard nothing, so the sequence
   stops instead of moving highlights silently). With a permanently missing file (716/724 before the fix) the
   remaining answers were never read; a transient failure such as the HTTP 429 above does the same. Please judge
   whether a definitive "not found" should skip to the next clip, and whether one retry is worth adding, without
   bringing back the "highlight moves with no sound" problem for non-readers.
4. Two rows are from the removed cache-verification draft calling an RPC that does not exist (already gone).

**Not tested on any Android device yet:** everything in sections 2.B to 2.H except what the owner clicked

## 5. Device acceptance plan (real Android phone, the candidate APK)

Pass = behaves as stated. Run each in both engines unless it says otherwise.

1. **Fresh install, online:** first screen appears quickly; welcome/mode clips play; disclaimer shows once.
2. **Fresh install, airplane mode:** app opens, bundled clips play, topic list appears from the fallback,
   an offline notice is shown, no crash.
3. **Slow / dropped network at first launch:** no second anonymous user is created; after reconnect the
   progress and topics load.
4. **Audio focus:** start a sign explanation, then take a phone call / start YouTube. The UI must show paused
   (never a false "playing"); after the call the clip resumes or can be resumed with ▶️; no overlap.
5. **Rapid taps:** hammer ▶️/⏸, switch questions fast, press back during audio. Never two voices; no stuck ⏸.
6. **Interrupted download:** turn the network off mid-download and kill the app; no corrupt file, the next
   play works.
7. **Developer option "Don't keep activities":** walk through quiz, exam, behavioral screens with audio.
8. **Voice answers (engine A, quiz and exam):** say answers 1, 2, 3 and 4; each recognized; mic permission
   denied path is graceful.
9. **Sign 302 video** plays and the explanation is not cut; closing the video does not leave silence.
10. **Diagnostics offline:** cause an error offline, reconnect; a row appears in `client_errors` with
    category/app_version/platform; it contains no personal data.
11. **Location:** primer then approve (city saved, sponsor ad by city); decline (any IP-derived city is wiped
    and not recomputed); share button sends the Play Store link; privacy page matches what happens.
12. **Full 30-question exam in each engine:** timings, result screen (pass mark is 26/30 via
    `api.PASS_FRACTION`), pass/fail clips, banner ad does not overlap the Android navigation bar.
13. **Sign 814** (road markings topic, "lane about to end"): text equals the approved text, 3 questions with
    4 answers each, feedback works. Expected new explanation length is about 35 s (old one was about 24 s);
    on a phone that cached the old file the old audio may play (known, section 6).
14. **Interface text:** the 12 strings appear in Amharic on their screens; no Hebrew visible in the UI.
15. **Upgrade path:** install production v8 from Play, use it, then install the candidate over it (no
    uninstall). Progress kept, audio plays, no crash. (Earlier an old Alpha build broke audio on upgrade; the
    cause was never proven.)
16. **Ads:** topic-page banners (17 topics x 2 engines) sit above the nav bar; app works with ads failing.
17. **Long session (20-30 min):** no memory growth or crash (SDK 56's Hermes regression was fixed in 57).
18. **Lifecycle:** app to background and back during audio, screen rotation lock, low-storage phone.

  manual bottom spacing to compensate, so swapping it is risky and is scheduled for the SDK 58 upgrade.
- `@expo/config-plugins` is kept as a dependency (expo-doctor warns); the ads-library key in `app.json`
  is intentional (section 2.A).

  bypass the 35-file FIFO limit and its list resets at startup.
- Microphone button behavior in engine A was reviewed and intentionally left as is.
- Retention: no automatic deletion of `client_errors` yet (the policy page therefore promises no number of days).
- SDK 58 follow-ups: SafeAreaView swap, Expo Go will support only SDK 58 (testing then needs the APK),
